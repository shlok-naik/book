# Minimalist AI Book Tracker

Flutter app ("cactus") for tracking reading progress via natural-language commands, with a Supabase backend, Google Books lookup, Groq-powered NL parsing, and RevenueCat purchases.

## Commands

```bash
flutter pub get                          # install dependencies
flutter run                               # run on connected device/emulator
flutter test                              # run all tests
flutter test test/library/library_controller_test.dart   # run a single test file
flutter analyze --fatal-infos --fatal-warnings   # static analysis — must be zero issues
dart format .                             # CI fails on unformatted code
flutter test integration_test/app_test.dart -d <device>   # end-to-end, on a real device/emulator
```

### Integration tests
[integration_test/app_test.dart](integration_test/app_test.dart) runs the real compiled app on a real device or emulator — real navigation, real animations, real platform channels — unlike everything under `test/`, which runs in a headless Dart VM. Only the bottom layer (Supabase/Google Books/RevenueCat) is faked, through `BookApp`'s own test seams (see § Composition root below) — the same fakes `test/widget_test.dart` already uses. Needs a connected device/emulator to run, so it isn't part of `flutter test`'s default run or CI; run it by hand with the command above.

### Branching
Every new feature gets its own branch off `main` (e.g. `feature/<short-name>`) — never commit new feature work directly to `main`. Bug fixes and polish for existing features may branch similarly (`fix/<short-name>`). Open a PR into `main` when the feature is ready rather than merging locally.

CI (`.github/workflows/ci.yml`) runs format, analyze, test, and a Deno
type-check of the edge functions on every push and PR. The analyzer rule
set in `analysis_options.yaml` is deliberately stricter than
`flutter_lints`' default — `unawaited_futures`, `discarded_futures` and
`use_build_context_synchronously` are promoted to errors — so treat a new
hint as a defect, not noise.

### Configuration
Resolved by [lib/core/env/env.dart](lib/core/env/env.dart) — never read `dotenv.env` directly anywhere else. Two sources, in order: compile-time `--dart-define`s, then a local `.env` file. `.env` is ignored outright in release builds (`Env._lookup` returns null under `kReleaseMode`) because it ships as a readable asset — a release missing a define shows `StartupFailureApp` rather than quietly starting on bundled values. Required: `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `REVENUECAT_API_KEY`. That is the whole list.

**No secret goes in either source** — both reach the device. The Groq API key used to live here and therefore shipped inside every build; it is now a Supabase project secret held by the `parse-command` edge function. The Google Books key went the same way: **Open Library is the backup.** Without that key Google's keyless daily quota is spent most days (Google answers 429, the proxy 503 — confirmed 2026-09-16), so `BookLookupService` (`_searchVolumes`) falls back to `OpenLibraryClient` ([open_library_client.dart](lib/features/library/data/open_library_client.dart), keyless `openlibrary.org/search.json`) on any Google failure but "no such book"/bad input, then **skips Google for `googleCooldown` (3 minutes)** instead of waiting on it again. Open Library results are `GoogleBook`s with id `ol:<work key>` (cached by `cache_book` like any id; `BookDetailsService.detailsFor` and `VolumeDetailPage` don't ask Google about them), covers `covers.openlibrary.org/b/id/<cover_i>-M.jpg`, and `ratings_count` for popularity. Every search is cached in memory 30 min; `coverFor(isbn:, title:, author:)` lookups (misses too) for the app's lifetime. Before any volume is cached, `_withCover` fills a missing cover from Open Library, so the shared `books` row gets it; and `CoverImage` asks `CoverImage.titleCoverResolver` (set in `main.dart` to `coverFor`) by title once a cover's own URL and ISBN cover both fail. `GOOGLE_BOOKS_API_KEY` **is** set; the remaining failures are Google's own random 503 "backendFailed" (≈40–60% of identical requests from the function, measured 2026-09-16). The `google-books` function (v5) therefore retries a 5xx up to 3 attempts with full-jitter exponential backoff within a 9s deadline and sends `country` (`GOOGLE_BOOKS_COUNTRY`, default `US`); `GoogleBooksApiClient` itself doesn't retry (`defaultRetryDelays` is empty) and leaves the rest to the Open Library fallback. It calls the `google-books` edge function (`/functions/v1/google-books/volumes[/<id>]`, a GET-only proxy with an allowlist of query params, deployed with `verify_jwt`), which adds `GOOGLE_BOOKS_API_KEY` from the project's secrets and passes Google's status and body through. Without that secret the function still answers, keyless, at Google's shared quota (expect 429s). If you find yourself adding a key that must stay private, it belongs on the server, not in `Env`.

A build missing a required key renders `StartupFailureApp` naming what is absent, rather than throwing at whichever screen first touches it.

### Database
Schema lives in [supabase/migrations/](supabase/migrations), applied in filename order — **not** a single re-runnable `schema.sql` (the old one truncated `user_books` on every run). Never edit an applied migration; add a new one with `supabase migration new <name>`, then `supabase db push`. Check `supabase db lint` or the dashboard advisors afterwards.

The hosted project's migration history does **not** match these filenames: migrations were applied there through the Supabase MCP/dashboard, which stamps its own timestamp (e.g. local `20260817000000_initial_schema.sql` is remote version `20260821175002`). A plain `supabase db push` will therefore refuse to run until the history is reconciled with `supabase migration repair`; compare `supabase migration list` first. Applying a new migration's SQL through the MCP `apply_migration` tool avoids that, at the cost of widening the mismatch. `20260912200000_drop_unused_profile_columns.sql` (drops `profiles.avatar_url`, the four old onboarding columns and the `avatars` bucket policies — the empty bucket itself must be deleted from the dashboard, since SQL deletes on storage tables are blocked) was written but **not yet applied** to the hosted project as of 2026-09-12 — check `list_migrations` before assuming either way. `20260914000000_book_details_tags_comments.sql` (detail/edition caches, tags, comments, owned edition, shelf order, the narrowed `touch_updated_at`) **was** applied through the MCP on 2026-09-13 as remote `book_details_tags_comments`, and `parse-command` was redeployed (v6) with the `add shelf`/`add tag`/`add comment` grammar. `20260914010000_keep_cached_page_count.sql` (remote `keep_cached_page_count`, same day) makes `cache_book_details` never replace an existing `books.page_count` — every reader's percentage hangs off it, and the volume endpoint often describes another printing.

`20260916000000_standalone_collections.sql` (custom `shelves` + `user_books.shelf_id`, standalone `tags` + `book_tags.tag_id` with a name-filling trigger, `reader_series` + `make_book_series`, and new versions of `set_book_series`, `replace_library`, `adopt_library` and `touch_updated_at`) was written on branch `feature/make-commands-custom-shelves` and **was** applied through the MCP on 2026-09-14 as remote `standalone_collections`; `parse-command` was redeployed (v8) with the `make shelf`/`make tag`/`make series`/`add series` grammar the same day. `20260917000000_local_series.sql` (remote `local_series`, same day) reworked series again, this time to be private per reader like a shelf or a tag: a `series` table replaces the shared `book_series`/`reader_series` pair, `user_books.series_id`/`series_position` replace the equivalent columns that lived on the shared `books` row, and `make_book_series`/`set_book_series` are gone — making and filing a series is now a plain insert/update under RLS. See **library** below for what that changed client-side.

Four migrations the client code on this branch depends on (the shelf query embeds `book_series`, and `cache_book` is called with `p_categories`) **were applied through the MCP on 2026-09-13** as remote `reading_goal_and_genres`, `book_series`, `replace_library` and `account_linking`: `20260915000000_reading_goal_and_genres` (`profiles.reading_goal`, `cache_book` stores categories and keeps an existing page count, and the **missing `reading_events` delete policy** — without it `delete <book>` never actually cleared journal lines), `20260915010000_book_series` (`book_series`, `books.series_id/series_position`, `set_book_series`), `20260915020000_replace_library` (the Goodreads import's one-transaction swap) and `20260915030000_account_linking` (`profiles.device_name/last_seen_at`, `library_summary()`, service-role-only `adopt_library`, and `touch_updated_at` ignoring owner changes). The two edge functions that go with them were deployed the same day: `parse-command` v7 (series grammar) and the new `link-account` v1, both with `verify_jwt`.

`20260918000000_delete_collections.sql` (delete policies on `shelves`/`tags`/`series`, for `remove shelf|tag|series` and the "+" panel's X) **is** applied on the hosted project as remote `delete_collections` (2026-09-14). `20260919000000_reread_count.sql` and `20260920000000_import_baseline.sql` (`user_books.imported`, `profiles.library_imported_at`, `mark_library_imported()`) are effectively applied on the hosted project (their columns exist; the migration history doesn't list them). `20260921000000_atomic_import_baseline.sql` (remote `atomic_import_baseline`, applied 2026-09-15) folds the baseline into `replace_library` itself and drops `mark_library_imported`. The `parse-command` prompt gained the `remove` grammar and the add-to-library rule in the same change but has **not been redeployed**.

`google-books` v1 was deployed through the MCP on 2026-09-15.

`20260923000000_popular_books_other_readers.sql` (`popular_books` counts only readers other than the caller, still needing two) was written 2026-09-17 but **not yet applied** to the hosted project — check `list_migrations` first.

Edge functions live in [supabase/functions/](supabase/functions) and deploy with `supabase functions deploy <name>`; their secrets are set with `supabase secrets set KEY=...`.

## Architecture

### Composition root
There is a single composition root: `_BookAppState` in [lib/main.dart](lib/main.dart). It builds `GoogleBooksApiClient`, `LibraryController` (with its `BookLookupService`, `UserBookRepository`, `ReadingEventRepository`, `BookNotesRepository` and a `BookDetailsService` sharing the one Google Books client — the detail page reaches the last two through `LibraryScope` rather than a scope of its own), `MemoryController`, and `SessionService` once, then injects them downward through `LibraryScope`, `MemoryScope` and `SessionScope`. Every one has a nullable constructor-injection seam (`libraryController`, `memoryController`, `sessionService` on `BookApp`) so tests can substitute fakes without touching Supabase/Google Books/Groq. Never instantiate an HTTP client or repository inside a widget — inject it from here (or thread it down from a caller that got it from here).

`_bootstrap` opens the session *before* the first frame. There is no sign-up step: `SessionService.ensureSession()` creates an anonymous Supabase user on first launch and reuses it forever after. Everything else depends on that — every feature reads through RLS on `auth.uid()` — so a failure there is a `StartupFailureApp`, not something to carry on past. **Anonymous sign-ins must be enabled on the Supabase project** (Auth → Providers, plus `enable_anonymous_sign_ins` in `supabase/config.toml` for local runs) or a fresh install cannot start.

`_bootstrap` then reads `OnboardingStore.hasSeen()` and passes `showOnboarding` to `BookApp`, which opens on `WelcomePage` or `RootShell` accordingly. It defaults to false so a widget test gets the app itself without saying so.

### Feature-first layout
Each feature under `lib/features/<name>/` is split into `data/` (repositories/API clients), `domain/` (models, business rules), and `presentation/` (`controllers/`, `pages/`, `widgets/`). `lib/core/` holds cross-feature concerns: `env/`, `supabase/`, `ai/` (Groq client), `purchases/` (RevenueCat), `theme/`, `widgets/`.

- **library** — the reader's shelf. `LibraryController` (a `ChangeNotifier`) is the single mutation point for shelf state — status, progress, rating, owned edition and manual order — whether the change comes from a typed command, a drag on `LibraryPage`, or `BookDetailPage`; it never talks to Supabase/Google Books directly, only through `BookLookupService` (cache-first: Supabase `books` table → Google Books API → write-back), `UserBookRepository`, `BookNotesRepository` and `BookDetailsService`. Every mutation is optimistic: local state updates and notifies immediately, then persists, rolling back on failure. `ReadingStatus` has four values — `toBeRead` (`to_be_read` on the wire), `reading`, `finished`, `dnf` — rendered as four sections: "reading", "to read", "finished", "did not finish". Every successful shelf command also fires-and-forgets a `ReadingEventRepository.log` call for the streaks page — a logging failure never affects the command's own success/failure result. Tags and comments are not journaled.
  - **The "+" panel ("make & remove")** has four tabs: shelves, tags, series — each chip under "yours" carries an X that unmakes it through the same `resolveRemoval`/`applyRemoval` path and confirmation as `remove <kind> <name>` — and **books**, a filterable list where each book's X removes it from the library (`LibraryController.deleteBookById`, confirmed with `confirmRemoveBook`).
  - **The "+" panel fades what can't be made** on the reader's plan: each tab's field and button sit in an `Opacity` (`make-<kind>-fade`) at 0.4 whenever `LibraryController.canMakeShelf`/`canMakeTag`/`canMakeSeries(PlanController.isPro.value)` says no — shelves always on the free plan, tags once 2 exist, series once 1 does — the same rule `_make` enforces, so the fade and the paywall-on-submit can't disagree.
  - **Collections are made first, applied after.** Custom shelves, tags and series are standalone ([lib/features/library/domain/collections.dart](lib/features/library/domain/collections.dart)): `LibraryController.makeShelf`/`makeTag`/`makeSeries` are the *only* creation paths, shared by the `make shelf|tag|series` commands, the library page's "+" panel (`showCollectionsSheet`) and the Goodreads import. `moveToShelf`, `addTag` (and the book page's tag field, via `findTag`) and `addToSeries` only look one up — an unknown name fails with the `make` command that would create it. Never add a path that creates a collection as a side effect of a book write. Names validate through `CollectionNames` (limits mirror the check constraints; the built-in shelf names and aliases — `tbr`, `to read`, `reading`, `finished`, `dnf`, `did not finish` — are reserved). `LibraryController.load` fetches `shelves`, `tags` and `mySeries` alongside the shelf; each degrades to its last value on failure.
  - **Custom shelves** are a *place*, not a reading state: `user_books.shelf_id` decides the section, `status` keeps meaning what it always did (stats, journal, "currently reading"). `ShelfRef` (`StatusShelfRef` | `CustomShelfRef`) names any section; `LibraryController.shelfSection(ref)`/`placementOf(entry)` place books (a `shelf_id` whose shelf didn't load falls back to its status section). Only `move` and drags change `shelf_id` — `finish`/`update` leave a book on its custom shelf.
  - **Shelf changes** all go through one path, `LibraryController._changeShelf` (or `moveBook(id, ShelfRef, index)`, which adds a reorder), applying `ShelfRules.enterShelf` ([lib/features/library/domain/shelf_rules.dart](lib/features/library/domain/shelf_rules.dart)), which wraps `ShelfRules.enter`: into **to read** or **reading** → page 0 (0%); into **finished** → the last page (100%; without a page count the page stays and `completion` reads 1.0 anyway) with a finish date; into **dnf** → progress kept; onto a **custom shelf** → only `shelf_id` changes; off a custom shelf onto the built-in shelf of the same status → progress kept. Moving anywhere but finished clears `finishedAt`; the rating is kept but only *shown* while finished. Only a status change is journaled. `move <book> <shelf>` (`moveToShelf`) adds a new book at that shelf (a custom shelf adds it as to-read) or **moves** one already on the shelf through that same path; only the shelf it's already on fails. `finishBook` uses the same rule. `updateProgress` changing status (a to-read book logged at page 40) does *not* reset — the typed page wins.
  - **Manual order**: `user_books.shelf_position` (null = never placed by hand). `LibraryController.section(status)` sorts via `ShelfRules.sortSection`: unplaced books first in natural (`updated_at` desc) order, then placed ones by position. `inProgress` is therefore in *shelf* order — the add tab's "currently reading" row uses `currentlyReading` (most recently updated reading book) instead, so dragging a book to the top isn't "reading it". `moveBook(id, status, index)` snapshots the whole shelf, applies the move and `ShelfRules.orderAfterDrop`, then writes `changeShelf` (if the status changed) and `saveShelfOrder` (the `set_shelf_order` RPC). If `changeShelf` fails the entire snapshot rolls back; if only `saveShelfOrder` fails, the saved move is **kept** (unplaced, as the server left it) and only the other books' positions roll back, with a failure message saying the spot didn't save — rolling the move back would show the book on a shelf the server no longer has it on. Dropping a book where it started returns a failure with a null message (no pill, no haptic).
  - **Library page: shelves are folders** (`LibraryPage`, Goodreads-style). The library tab (`LibraryPage()`) lists every shelf — reading, to read, the reader's custom shelves oldest first, finished, did not finish — as a `_ShelfFolder` row (keyed `shelf-folder-<status name | custom-<id>>`): a fanned stack of its first three covers (an outlined blank one when empty), the name, "N books" and a chevron, one semantics button node ("Reading, 2 books"). The **series** row sits under the to-read folder behind its own collapse chevron (starts closed). Tapping a folder calls `openShelf(context, ref)` (route name `shelf`), which pushes `LibraryPage(shelf: ref)`: a `SettingsHeader` with the shelf's name over that one shelf's cover grid, or a wordless outlined `_EmptyShelf` (keyed `empty-shelf-<key>`) when it has no books; a custom shelf that no longer exists says so. There is **no** instructional or "nothing here" copy anywhere (a load *error* still replaces the folders with the retry message). **Only a shelf page can drag**: `LongPressDraggable` tiles reorder by dropping on another tile (accent insertion bar, left half = before, right half = after), and picking a book up slides `_DragActions` down *over* the header — Pixel-style, nothing reflows — with two targets: **move to…** (`showShelfSelectionSheet`, then `_move(id, ref, 0)`) and **remove**, the bin (`confirmRemoveBook`, exactly like `delete <book>`, then `deleteBookById`). The page auto-scrolls near the top/bottom edges. While a move is saving (`_moving`), no book can be picked up (`maxSimultaneousDrags: 0`) and keyboard moves are ignored. Every move — drag, keyboard, screen reader — goes through `_move`, which catches unexpected errors, sets haptics, and shows the confirmation pill as a live region. Tiles are `FocusableActionDetector`s: Enter/Space opens the book, Alt+↑/↓ moves to the previous/next shelf, Alt+←/→ earlier/later; plus `CustomSemanticsAction`s ("Move to finished", "Move earlier"…) merged into the tile's one semantics node. **Searching** the library tab swaps the folders for every matching book grouped under its shelf's heading (`_SectionHeading`), with nothing draggable. A tap opens `BookDetailPage` via `openBookDetail` (route name `book_detail`). **Grid cell height** is the cover plus `BookTile.textExtent(context)` — measured with `TextPainter` from the same `BookTile.titleStyle`/`subtitleStyle`/`labelStyle` the tile and the grouped series tile draw with, in the reader's fonts and text scale, and recomputed when `PaintingBinding.systemFonts` notifies (Google Fonts land after the first frame). Never hardcode it: the old fixed 86px overflowed every rated tile with real fonts or larger phone text. **Covers** go through `CoverImage` ([book_cover.dart](lib/features/library/presentation/widgets/book_cover.dart)): the cached Google cover, then Open Library by ISBN (`covers.openlibrary.org/b/isbn/<isbn>-M.jpg?default=false`), then the typographic placeholder — so every `BookCover` call site passes `isbn: book.isbn13 ?? book.isbn10`. `BookLookupService._bestMatch` prefers a volume with a thumbnail within each match tier, since whichever volume is cached is the cover every reader of that book sees.
  - **Book info page** (`BookDetailPage`, [lib/features/library/presentation/pages/book_detail_page.dart](lib/features/library/presentation/pages/book_detail_page.dart)) holds a `user_books` id, not a snapshot, and reads the row from `LibraryController.findById` every build. Layout, top to bottom: heading (cover, title as a semantic header, subtitle, author, a status line such as "reading · 78%" / "did not finish · stopped at 34%", the owned edition); a facts strip (pages, published via `formatPublishedDate`, publisher, language); a single **editions** row; "your reading" (page/percent fields kept in sync through `LibraryController.pageForPercent`, and a `StarRatingInput` that only works on finished books — keyboard arrows/Home/End, one adjustable slider node to screen readers); tags; comments (a DNF book's field asks "why didn't you finish it?"); about (blurb, genre, ISBN, Google rating). "your reading" also has a **dates** row (not for a book queued to read): `started on` and, for a finished book, `finished on`, each a button opening a `showDatePicker` (no future dates; a start can't be after the finish, but a finish picked *before* the start moves the start back with it — a book added straight onto finished starts and finishes the same day, and bounding the finish by that start offered only today), saved through `LibraryController.setDates` (optimistic with rollback; refuses future dates, a finish before the start, and a finish date on an unfinished book) → `UserBookRepository.saveDates`. The dates are filled in automatically: `start` (and its `[date]`) writes `started_at`, any move into reading stamps it (`ShelfRules.enter`), and `finish`/moves into finished stamp `finished_at`. Every action has a button, so no command is ever needed: "your reading" opens with a **shelf** row (`showShelfSelectionSheet`, [shelf_selection_sheet.dart](lib/features/library/presentation/widgets/shelf_selection_sheet.dart) → `LibraryController.moveBook(id, ref, 0)`, the same path a drag takes) and, for a finished book, **read again** (`LibraryController.restartBookById`); the page ends with **remove from library** (confirmed with `confirmRemoveBook`, then `deleteBookById` and a `maybePop`). A restarted book wears **star stickers** on its cover (`RereadStickers` in `book_cover.dart`, fed `rereadCount` and whether it is finished): restarting adds one, finishing that pass a second — bronze for the first re-read, silver for the second, gold for the third and every one after, capped at two gold stars. Every `BookCover` call site passes `finished:` alongside `rereadCount:`. Its tag field applies only tags that were made (`BookDetailController.findTag`). Sections are `InfoSection` ([lib/features/library/presentation/widgets/info_section.dart](lib/features/library/presentation/widgets/info_section.dart)): `SettingsSection`'s look, with the caption announced as a heading. Everything but the shelf row is per-page state in `BookDetailController`: four independently loading `DetailSection`s (details, editions, tags, comments), so Google Books failing never blanks the reader's own notes; tag/comment edits there are optimistic with rollback, and page-level actions go through `_run`, which turns unexpected throws into a visible failure.
  - **Owned edition = the reader's copy.** `fetchLibrary` embeds the owned `book_editions` row (`owned_edition:book_editions!user_books_owned_edition_fkey(*)`) into each `LibraryBook.ownedEdition`, and `LibraryBook.displayBook` (`Book.withEdition`) is the book as *their* copy: the edition's cover, page count, publisher, published date, ISBN and language over the work's, falling back to the work only for cover and page count; title, author, blurb, genre and ratings stay the work's so commands still match. Every surface that shows a book (library tile, currently-reading card, book page) renders `displayBook`, and `LibraryBook.pageCount` — so progress, validation and "last page = finished" — follows the owned edition. `LibraryController.setOwnedEdition(id, BookEdition?)` rescales the page to keep the reader's percentage (`ShelfRules.pageForEdition`: finished stays at the new last page, an unfinished book never lands on it) and writes edition + page in one update. The shared `books` row is never changed. `_upsertLocal` keeps a row's edition when a replacement was built without one. The book page's editions row always shows the edition *count* on the right and, when one is owned, "yours: ebook · Penguin · 2010" on a second line — it must not swap one for the other.
  - **Editions page** (`EditionsPage`, opened only via `openBookEditions`, route name `book_editions`): a gallery grid of covers (`BookCover`, placeholder when Google has no image) with the publisher and format · year under each; tapping (or Enter on) a cover marks it as the owned edition through `LibraryController.setOwnedEdition`, tapping again clears it, and taps are locked while one save is in flight. It is handed the detail page's own `BookDetailController` rather than building one, so already-loaded editions show instantly and nothing is fetched twice; if editions failed or never loaded, it retries after its first frame (not in `initState` — the controller's notify would dirty the detail page mid-build). Loading, error-with-retry, empty and book-gone states are all distinct.
  - **Detail/edition caching** (`BookDetailsService`, same shape as `BookLookupService`): extended info lives in extra `books` columns, editions in the shared `book_editions` table; both are written only by security-definer RPCs (`cache_book_details`, `cache_book_editions`). A `details_fetched_at`/`editions_fetched_at` stamp on `books` — never emptiness — decides hit vs miss, so "Google has no editions for this" is cached too. The shelf's copy of a `Book` may predate a fetch, so a miss re-reads the `books` row before calling Google. Cache *reads* that fail degrade to a miss; a failed *details* write still returns what was fetched; a failed *editions* write is an error (an uncached edition has no id and can't be owned). `EditionFilter` ([lib/features/library/domain/edition_filter.dart](lib/features/library/domain/edition_filter.dart)) keeps only ebook (`saleInfo.isEbook`) and physical (a `BOOK` with an ISBN) editions whose main title matches exactly and whose author matches by name-token subset (a shared surname isn't enough — Brian Herbert's "Dune: The Heir of Caladan" is not an edition of Frank Herbert's "Dune"), dropping study guides/summaries/audio/box sets. Google's HTML blurbs go through `plainTextFromHtml` before caching. `LibraryController._warmEditions` fires `editionsFor` fire-and-forget right after a book lands on the shelf (`startBook`, `startBookByIsbn`, `moveToShelf`'s "not on the shelf yet" branch) — a no-op once `hasCachedEditions`, and any failure is only logged — so a reader who opens the editions page later almost always finds a cache hit instead of a live Google Books search.
- **logging** — the natural-language "+"/log page. `LogCommandParser` turns text into the command grammar: `start <book> [date]`, `start isbn [date]`, `update <book> <page or percent%> [date]` (a bare number is a page, `N%` a percentage), `finish <book> [date]`, `rate <book> <stars>`, `delete <book>`, `move <book> <shelf>` (built-in or custom; see **library** above), the make-first collection commands `make shelf <name>`, `make tag <tag>`, `make series <name>`, `add tag <tag> <book>` (one word, or quoted), `add series <series> [#n] <book>`, and `add comment <comment> <book>` — plus two "cactus pro"-only commands that only ever arrive as an AI-extracted line, never typed directly — `remember <book> :: <note>` and `recommend <book> :: <reason>`. The `isbn` argument to `start` opens the camera rather than naming a book: `HomePage` recognizes the bare keyword before it ever reaches the parser and calls `scanIsbn` ([lib/features/logging/presentation/pages/isbn_scanner_page.dart](lib/features/logging/presentation/pages/isbn_scanner_page.dart)), a pushed `IsbnScannerPage` (named route `isbn_scanner`) built on `mobile_scanner`, restricted to the barcode formats an ISBN is actually printed as (EAN-13, EAN-8, UPC-A). The first frame that decodes pops the page with that value; the header's back chevron pops with `null`, which `HomePage` treats as a cancel rather than resubmitting. A resolved code is spliced back into the field as `start isbn <digits>[ date]` and re-parsed normally, so `BookLookupService`'s existing ISBN lookup does the rest. Camera access needs `NSCameraUsageDescription` (`ios/Runner/Info.plist`) and `android.permission.CAMERA` plus an optional `android.hardware.camera` feature (`android/app/src/main/AndroidManifest.xml`); a denied or unavailable camera shows in-page copy rather than a raw plugin exception. `start`/`update`/`finish` also take an optional trailing `YYYY-MM-DD` — "I started Dune yesterday" backdates the `reading_events` row it logs (and so the streaks day it lands on), never the shelf write itself, which always reflects when the command actually ran; `LibraryController` rejects a future date before it ever reaches Supabase. Resolving "yesterday" needs the reader's own local "today", which only the client can know — `EdgeFunctionCommandParser` sends it on every request as `context.today`. `AiCommandParser` ([lib/core/ai/ai_command_parser.dart](lib/core/ai/ai_command_parser.dart)) is the "cactus pro" alternative that asks an LLM to split a free-form sentence into that same grammar before handing it to the identical parser — the two entry points converge on one command surface. The real implementation calls the `parse-command` edge function; the model provider's key never reaches the device. `delete` asks first: `HomePage._confirmDelete` shows `showConfirmDialog` ([lib/core/widgets/confirm_dialog.dart](lib/core/widgets/confirm_dialog.dart), also used by import and account linking); cancelling returns `LibraryActionResult.cancelled`, which gets no haptic and `CommandOutcome.dismissed` — the text stays in the field without a shake. `HomePage` gates `remember`/`recommend` on `PlanController.isPro` at the point they'd run, not in the parser — recognizing the syntax and being allowed to act on it are kept as two separate concerns. `recommend` never touches the shelf or the memory list: the edge function has already resolved a title and reason by the time the line reaches the client, grounded in the reader's shelf titles and `memory` notes sent as optional `context` on the same request. The `add` family puts its own argument *before* the book so the title is always the free-form tail; `move` puts the shelf *after* it, so a quoted shelf (`move Dune "summer reads"`, what the AI always emits) is split by the parser, and an unquoted one arrives with `title == null` and the whole `argument`, split by `LibraryController.moveToShelfUnsplit` against the shelves that exist (longest trailing shelf name wins). The pill shows the library's message for every `move` and for any command without a parsed title. A quoted comment (`add comment "x" Dune`, straight or curly quotes) is split by the parser; an **unquoted** one has `title == null` and its whole argument in `note`, and `LibraryController.addComment` splits it with `splitTrailingTitle` (longest trailing run of words naming a shelf book, exact before fuzzy) — `HomePage._applyToLibrary` routes that case *before* its "no title" check, and uses the library's result message for the pill since the parser couldn't name the book. **Add-to-library fallback:** `update` (page or percent), `finish`, `rate`, `add tag`, `add series` and a *quoted* `add comment` no longer refuse a book that isn't on the shelf — `LibraryController._onShelfOrAdd` resolves the title cache-first like `move` and adds it at the shelf the command implies (reading for `update`; finished, at its last page, for `finish` and `rate`; to read for the `add` family), journaled like a `move` add, with the command's date as its start/finish date. Each command's own validation (page range, percent needing a page count, rating range, the tag/series existing, the comment being valid) runs *before* the add, against a stand-in row, so a typo never leaves a stray book. A hit on the shelf still resolves synchronously so the optimistic update redraws in the same frame. The result carries `LibraryActionResult.addedToLibrary`, which makes `HomePage` show the library's message ("Added "Dune" as finished") instead of the parser's. `restart`, `delete`, an unquoted `add comment` and the `remove` family still need the book on the shelf. `start` on a book already queued *to read* now moves it to reading instead of refusing. **Remove:** `remove shelf|tag|series <name> [book]` and `remove comment [comment] <book>` (enum values `removeShelf`/`removeTag`/`removeSeries`/`removeComment`). With a book they take it out (`removeFromShelf` — progress kept, back to its status section; `removeTag`; `removeFromSeries`); with no book they unmake the collection (`deleteShelf`/`deleteTag`/`deleteSeries` — books fall back via the `on delete set null (col)` foreign keys, mirrored locally). A quoted name is split by the parser; an unquoted remainder goes to `LibraryController.resolveRemoval`, which takes the *longest* leading run of words naming an existing collection and treats the rest as the title, returning a sealed `CollectionRemoval` (`UnmakeCollection` | `RemoveFromCollection`, [lib/features/library/domain/collections.dart](lib/features/library/domain/collections.dart)); built-in shelves can't be removed. `remove comment` resolves via `resolveCommentRemoval` (named comment by case-insensitive exact then prefix match, otherwise the latest). Unmaking a collection and removing a comment are confirmed first, with the wording in `removal_confirmations.dart` shared with the "+" panel (so is `delete`'s). `CollectionKind` moved to the domain file and is re-exported from `collections_sheet.dart`. Tags/comments otherwise need the book on the shelf. **`CommandCatalog`** ([lib/features/logging/domain/command_catalog.dart](lib/features/logging/domain/command_catalog.dart)) is the single source of command help — the parser's "did you mean" suggestions, the settings commands page and its test all read it, and `command_catalog_test.dart` parses every example; add a command there when you add one to the grammar, and to the `parse-command` prompt.
  - **Parser modes.** `HomePage._run` asks `ParserModeController.effective(offline:)` ([parser_mode_controller.dart](lib/features/logging/presentation/parser_mode_controller.dart)) which parser reads a line: **classic** (`_runManual`, `LogCommandParser` alone), **beta** (`_runSmart`) or **pro ai** (`_runAi`). In debug builds the settings debug switch sets `ParserModeController.chosen` (`shared_preferences`, initialized in `_bootstrap`); unset — and always in release — it follows the plan (`planDefault`: pro ai for cactus pro, **the beta parser for every free reader** — it is the free plan's main way in). Offline, pro ai falls back to beta, which runs on the device. A single typed command that only had its title matched to the shelf ("delete dune" → `delete Dune`) still runs as a plain manual command, keeping the field's own accept/shake/cancel behaviour. **The beta parser** is `SmartCommandParser` ([smart_command_parser.dart](lib/features/logging/domain/smart_command_parser.dart)) — pure, no model, free for every reader: it splits a message into actions on sentence ends, "and"/"then"/commas (only where the next piece names an action, so "Pride and Prejudice" stays whole; "four and a half" is joined first and a decimal point never ends a sentence), recognises each action from everyday phrasing (started / on page 40, 40%, halfway / done with, finished / 4 stars, rated 3/5 / gave up on → `move … "dnf"` / want to read → `move … "tbr"` / re-reading → `restart` / get rid of → `delete`), pulls out dates (yesterday, last night, N days ago, a weekday, ISO) into the grammar's trailing `YYYY-MM-DD`, and matches titles against the shelf forgiving typos (optimal-string-alignment distance: 1 edit from 4 letters, 2 from 8), stop words and the author's own name. "it"/an empty phrase means the book just mentioned in the same message, else the one being read. It also **organises in words** (`_parseOrganise`, tried before anything else so "move dune to summer reads" isn't read as a classic move of "dune to"): "make a shelf called x" / "create a new tag x" / "new series x" → `make`; "tag dune as sci-fi" / "add cosy to circe" → `add tag`; "put dune messiah in the dune series as #2" → `add series`; "note on dune: …" / "comment on dune that …" → `add comment`; "move/put dune on|to <shelf>" → `move`, only for a built-in shelf or one in `shelves` (the reader's own, passed by `HomePage`). Lines that already parse as commands still get their title polished ("finish dnue" → `finish Dune`). It returns sealed `SmartLine`s: `ResolvedLine` (grammar), `UnrecognizedLine` (run as typed so it fails with the usual message) and `NeedsBookLine` — no book named and nothing being read, or several close shelf matches none of which is being read — for which `HomePage._askForBook` opens `showBookPicker` (a `CataloguePick` is cached with `lookup.resolveVolume` first so the command finds that exact book). A title with nothing close on the shelf passes through for the library's add-to-library fallback to find on Google Books. **Commands are never shown.** The resulting lines — and the AI's — run through `HomePage._runLines`: in order, each via `_runCommand`, with every outcome said in one plain-language pill (successes first, then failures, joined by " · ", e.g. `Started "Dune" · On page 120 of "Dune"`); a line that isn't a command fails as "Didn't catch that.", never with command-syntax suggestions. The `CommandInput` stays mounted the whole time (so the keyboard stays up): it strikes through when anything was done and shakes when nothing was. The old `InstructionRow` list is gone. Command outcome messages are written as sentences ("On page 120 of", "40% through", "Rated … 4 stars", "Tagged … as", dates as " on Aug 31"). A line that came back unchanged runs as a plain manual command.

### Offline mode
The shelf and journal keep working without a connection, and sync when it comes back.

- **Connectivity** — `ConnectivityController` ([lib/core/network/connectivity_controller.dart](lib/core/network/connectivity_controller.dart)), a static `isOffline` notifier fed by `connectivity_plus` (no interface = offline), a reachability probe to Supabase's `/auth/v1/health` (any HTTP answer = online), and `runSupabase` reporting transport failures/successes. Re-probes every 20s while offline. **Inert until `attach()`** (called from `_bootstrap`) — tests never run `main`, so it stays online and every report is a no-op; `debugSetOffline`/`reset` are the test seams.
- **Indicator** — `OfflineIndicator` ([lib/core/widgets/offline_indicator.dart](lib/core/widgets/offline_indicator.dart)) sits just left of the right-hand icon in both `TopBar` and `SettingsHeader`, i.e. on every page. Nothing while online and idle; a crossed-out cloud while offline (tap → a sheet saying what still works and how many changes wait); a syncing cloud while queued writes drain. Reads the queue through the optional `SyncScope` (installed by `MaterialApp.builder` in `main.dart`).
- **Cache + queue** — `OfflineLibraryCache` ([lib/features/library/data/offline_library_cache.dart](lib/features/library/data/offline_library_cache.dart)) keeps the last server answer as **raw rows** (`user_books` with `book`/`owned_edition` embedded, and each year's `reading_events`) in a per-account `FileOfflineStore` (application support dir, `offline/<uid>/`). An offline write patches the cached row with exactly the values it would have sent — re-parsed by the same `fromRow` code, so there's no second serialization — emulating only what local ordering needs from `touch_updated_at` (bump `updated_at` unless position-only; clear `shelf_position` on a status/shelf change). The identical request goes into `PendingWriteQueue` as a `PendingUpdate`/`PendingInsert`/`PendingDelete`/`PendingRpc` (absolute sets only, so in-order replay is safe; consecutive updates to the same row merge). The cache is inactive the moment the signed-in uid differs from its account (an email link that swapped libraries).
- **Repositories** — `UserBookRepository` and `ReadingEventRepository` take an optional `offline` cache (null = the old online-only behaviour, which every test without it gets). Writes to existing rows (`saveProgress`, `changeShelf`, `saveShelfOrder`, `rate`, `restart`, `setOwnedEdition`, `delete`; `log`, `deleteForTitle`) go to the server, and on a `NetworkException` — or immediately when `OfflineLibraryCache.mustQueueWrite()` says so: known offline, **or online with older writes still queued** — queue + patch and return the patched row (then `syncSoon()`), so `LibraryController`'s optimistic updates never roll back. Queueing behind waiting writes is what keeps replay ordered: a direct write right after reconnecting would land before the queue and then be overwritten by an older replayed value. Reads drain the queue first and answer from the cache while writes are still pending or the server is unreachable. `FileOfflineStore` serializes writes per key (overlapping writes used to share one `.tmp` file and could corrupt the queue, which reads back as empty). **Adding a new book still needs a connection** (it needs a catalogue row and a server id); `start`/`addWithStatus` now select with the embedded book so a just-added book is patchable offline. Tags, comments, series filing, collections, memories and goals remain online-only.
- **Sync** — `SyncCoordinator` ([lib/core/offline/sync_coordinator.dart](lib/core/offline/sync_coordinator.dart)) drains at startup and on every reconnect, strictly in order, re-snapshotting until the queue is empty (so writes queued mid-drain go out in the same flush); `flush` never throws: stops at the first unreachable write, **drops** a write the server refuses (counted in `lastRejected`), and afterwards calls `onSynced` (`LibraryController.load`) *outside* the drain — a load drains before it reads, so calling it inside would deadlock. Conflicts are last-write-wins; `updated_at` is stamped by the server at sync time.
- **AI offline** — cactus pro's natural language is an edge function, so `HomePage._run` sends a pro reader's line to the manual parser while offline.

### Supabase model
`user_id` columns default to `auth.uid()` at the database level (never set by app code) and RLS is what actually enforces per-reader isolation — anonymous Supabase Auth sessions still get a real `authenticated` role. Every policy calls `(select auth.uid())`, not the bare function, so the planner evaluates it once per query rather than once per row.

- `books` — the shared Google Books cache. Readable by any signed-in reader, **writable by none**: the sole write path is the `cache_book()` security-definer function, because a table-level insert/update grant would also let any reader rewrite or delete rows out from under everyone else.
- `book_editions` — the shared edition cache, same rules as `books`: readable by any signed-in reader, written only by `cache_book_editions(book_id, jsonb)` (upserts on `(book_id, google_books_id)` so an owned edition's id survives a re-fetch; stamps `books.editions_fetched_at`). A check constraint allows only `format in ('ebook','physical')`. `books` also gained extended-info columns written only by `cache_book_details` (updates an existing row, never inserts; stamps `details_fetched_at`).
- `shelves`, `tags`, `series` — the reader's standalone collections, private per reader, all three the same shape (`id`, `user_id` defaulting to `auth.uid()`, `name`). `user_books (user_id, shelf_id)`, `book_tags (user_id, tag_id)` and `user_books (user_id, series_id)` are composite foreign keys onto them (`on update cascade`, so `adopt_library` can move owners), and `book_tags.tag` is filled from `tags.name` by the `book_tags_fill_name` trigger, never sent. All three are plain client inserts under RLS — no security-definer function stands between a reader and their own collection.
- `user_books`, `reading_events`, `profiles`, `memories`, `book_tags`, `book_comments` — private per reader. `book_tags`/`book_comments` hang off `user_books.id` (`on delete cascade`, so deleting a book takes its notes), and their insert policies also check the `user_books` row belongs to the caller; tags are unique per book on `lower(btrim(tag))`. `user_books.owned_edition_id` has a composite FK `(book_id, owned_edition_id) → book_editions(book_id, id)`, so an owned edition is always an edition of that book. `user_books.series_id`/`series_position` are the reader's own filing, independent of `shelf_id`/`status` — only `add series` ever changes them. `user_books.updated_at` is maintained by the `user_books_touch_updated_at` trigger, never sent from the client (the shelf is ordered by it, so a skewed device clock could otherwise pin its own rows to one end forever). That trigger (`touch_updated_at`, also used by `book_comments`) leaves `updated_at` alone for a write that changes only `shelf_position` — a drag must not change which book is "currently reading" — and clears `shelf_position` on a status change that doesn't set one. `set_shelf_order(uuid[])` is `security invoker`; RLS limits it to the caller's rows.
- `ai_requests` — the AI rate-limit ledger. RLS enabled with *no policies at all*, deliberately: it is reachable only through `claim_ai_request()`, so a reader cannot clear their own history to reset their limit.
- A trigger (`handle_new_user`) creates a blank `profiles` row on first auth, so app code only ever `UPDATE`s it. Its `EXECUTE` grant is revoked from `anon`/`authenticated` — it is a trigger function, not an API.

### Errors, logging and startup
**Every message a reader sees is as short as it can be** — a few words, no apology, no "we", no "try again in a moment" ("You're offline.", "Couldn't save tag.", "No shelf \"x\". Try: make shelf x"). Repositories translate driver failures into exceptions carrying a message already safe to show (`LibraryException`, `OnboardingException`, `AiCommandException`); controllers turn those into result objects. The UI never renders a raw driver error — and never silently swallows one either: a load that failed must look different from a load that came back empty (see `StreaksController.errorMessage`).

Command outcomes are shown by `ConfirmationPill` ([confirmation_pill.dart](lib/features/logging/presentation/widgets/confirmation_pill.dart)) — deliberately **not** a grey chip: a mark whose shape says how it went (`ConfirmationTone.success` accent check, `.failure` ink cross, `.neutral` dash for a cancel or plain information) beside the unchanged message, with quoted titles set in the book-title face. Pass the tone from the result at every call site. Only where it floats over content (the library grid, `floating: true`) does it get a background — the page's own paper with a divider hairline.

A UI entry point that awaits a handler must survive the handler throwing: `CommandInput._submit` treats a throw as `rejected` (a stuck busy flag used to leave the add tab's field read-only for the session), and `HomePage._runCommand` turns any unexpected error into a failed line with a message. Loads that callers await **join** an in-flight load rather than returning early (`LibraryController.load`, `StreaksController.load`), and a reset/reload after the data was replaced supersedes the stale in-flight one. Numbers written in copy (ratings, percentages, series numbers, CSV) go through `formatCompactNumber`/`roundToHalf` ([lib/core/formatting/numbers.dart](lib/core/formatting/numbers.dart)) — never a hand-rolled `toInt()`, which throws on the infinity a long run of typed digits parses to.

All diagnostics go through `AppLogger` ([lib/core/diagnostics/app_logger.dart](lib/core/diagnostics/app_logger.dart)) — never `print`/`debugPrint`, which are compiled out of release builds. For fire-and-forget work use `reportingFailure(...)` rather than `unawaited(x.catchError((_) {}))`, so the failure is recorded instead of dropped. `main` installs `FlutterError.onError`, `PlatformDispatcher.instance.onError` and a guarded zone, and all three feed `AppLogger`.

`CrashReporter` ([lib/core/diagnostics/crash_reporter.dart](lib/core/diagnostics/crash_reporter.dart)) attaches Firebase Crashlytics to `AppLogger.sink` — the single seam, never at individual call sites. Two rules: **never** also assign `FirebaseCrashlytics.instance.recordFlutterFatalError` to `FlutterError.onError` (Firebase's own guide says to; `main` already owns it, and doing both double-reports every framework error), and every `CrashReporter` entry point must stay inert until `attach()` succeeded — `FirebaseCrashlytics.instance` throws *synchronously* without Firebase, so an unguarded call takes out its caller rather than merely failing to report. Widget tests never run `main`, so that is the normal state in tests, not an edge case.

### Accessibility and feel
The UI is icon-heavy and text-light, which is precisely the combination that makes an app unusable with VoiceOver/TalkBack unless the labels are deliberate. The tab bar, book tiles and every day on the streak grid carry explicit `Semantics` — a book tile is *one* node reading "Dune by Frank Herbert. Page 150 of 300, 50 percent.", not six fragments ending in five unlabelled star icons. `test/accessibility/semantics_test.dart` pins these down.

Haptics go through `AppHaptics` ([lib/core/feedback/app_haptics.dart](lib/core/feedback/app_haptics.dart)) and have exactly three meanings: `selection()` (you moved), `accepted()` (it worked), `rejected()` (it didn't). Never fire one from a timer, a background event or a screen appearing — only in direct response to a touch the reader just made, and never when the outcome is a no-op (tapping the tab you are already on).

The app is portrait-only, declared in the Android manifest, the iOS plist *and* `SystemChrome` — the streaks page fits a whole year on one screen and has nowhere to put December in landscape. That page scrolls only when it must (large accessibility text sizes), never otherwise.

### Analytics
`AppAnalytics` ([lib/core/analytics/app_analytics.dart](lib/core/analytics/app_analytics.dart)) rides on the Firebase app `CrashReporter.attach()` initializes, and follows the same inert-until-attached rule for the same reason. Screen views come from `RouteSettings` names through a navigator observer on `MaterialApp` — **a new pushed route needs a `settings: const RouteSettings(name: ...)` or it disappears from the funnel silently** (the settings screen and the paywall popup both carry one). Paywall/purchase outcomes are explicit calls instead, and distinguish cancelled from store_error from entitlement_inactive, since those three call for completely different fixes.

Hard rule: **no reader-authored content is ever sent** — no titles, authors, commands, profile answers or emails. Parameters are screen names or enum-like constants only.

### Theming
`AppColors` is a `ThemeExtension` (light/dark instances in [lib/core/theme/app_colors.dart](lib/core/theme/app_colors.dart)) registered on `ThemeData.extensions` in [lib/core/theme/app_theme.dart](lib/core/theme/app_theme.dart); widgets read colors via `context.colors`, never a hardcoded hex. `ThemeController` (a `ValueListenable<ThemeMode>`) drives the `MaterialApp.themeMode` switch in `main.dart`.

## 🏗️ Production-Ready Modular Code Guidelines

### 1. Feature-First Architecture
Organize the codebase by feature domain rather than technical layers. 
*   **Good**: `features/book_tracking/`, `features/ai_summary/`, `features/library/`
*   **Avoid**: Grouping all models in one folder, all UI components in another.
This isolation ensures that changes to the AI feature don't accidentally break the core book tracking logic.

### 2. Separation of Concerns (Dumb UI)
Keep your UI components strictly focused on presentation. Extract all business logic, API calls, and data transformations into dedicated state management controllers or view-models. The UI should only listen to state changes and dispatch user actions.

### 3. Dependency Injection
Never instantiate HTTP clients or AI service classes directly inside your UI or business logic. Inject them. This makes it trivial to swap out a real AI backend for a mocked version during testing or development, avoiding unnecessary API costs.

### 4. Theme Extensions
Do not hardcode the hex values from the design system directly into UI components. Define the Light and Dark schemes centrally using theme extensions. This ensures that toggling between the Light and Dark modes updates the entire app consistently and instantly.

## 🧪 Testing Strategy

### Unit Tests
*   **Focus**: Business logic, data parsing, and AI prompt generation.
*   **Action**: Ensure that your data models accurately serialize and deserialize the AI's responses (especially if parsing JSON from an LLM). Test edge cases, such as network timeouts or malformed AI output, to ensure the app degrades gracefully rather than crashing.

### Component / UI Tests
*   **Focus**: Reusable UI elements (e.g., the accent progress ring, book cover cards, AI summary bottom sheets).
*   **Action**: Render these components in isolation. Verify that the progress bar accurately reflects 0%, 50%, and 100% states. Ensure the text contrast remains readable in both Light and Dark themes.

### Integration Tests
*   **Focus**: Core user journeys.
