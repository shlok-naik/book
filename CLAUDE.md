# Minimalist AI Book Tracker

Flutter app ("cactus") for tracking reading progress via natural-language commands, with a Supabase backend, Google Books lookup, Groq-powered NL parsing, and RevenueCat purchases.

## Commands

```bash
flutter pub get                          # install dependencies
flutter run                               # run on connected device/emulator
flutter test                              # run all tests
flutter test test/library/library_controller_test.dart   # run a single test file
flutter analyze --fatal-infos --fatal-warnings   # static analysis — must be zero issues
dart format .                             # CI fails on unformatted code
```

### Branching
Every new feature gets its own branch off `main` (e.g. `feature/<short-name>`) — never commit new feature work directly to `main`. Bug fixes and polish for existing features may branch similarly (`fix/<short-name>`). Open a PR into `main` when the feature is ready rather than merging locally.

CI (`.github/workflows/ci.yml`) runs format, analyze, test, and a Deno
type-check of the edge functions on every push and PR. The analyzer rule
set in `analysis_options.yaml` is deliberately stricter than
`flutter_lints`' default — `unawaited_futures`, `discarded_futures` and
`use_build_context_synchronously` are promoted to errors — so treat a new
hint as a defect, not noise.

### Configuration
Resolved by [lib/core/env/env.dart](lib/core/env/env.dart) — never read `dotenv.env` directly anywhere else. Two sources, in order: compile-time `--dart-define`s, then a local `.env` file. `.env` is ignored outright in release builds (`Env._lookup` returns null under `kReleaseMode`) because it ships as a readable asset — a release missing a define shows `StartupFailureApp` rather than quietly starting on bundled values. Required: `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `REVENUECAT_API_KEY`. Optional: `GOOGLE_BOOKS_API_KEY` (missing degrades to keyless search).

**No secret goes in either source** — both reach the device. The Groq API key used to live here and therefore shipped inside every build; it is now a Supabase project secret held by the `parse-command` edge function. If you find yourself adding a key that must stay private, it belongs on the server, not in `Env`.

A build missing a required key renders `StartupFailureApp` naming what is absent, rather than throwing at whichever screen first touches it.

### Database
Schema lives in [supabase/migrations/](supabase/migrations), applied in filename order — **not** a single re-runnable `schema.sql` (the old one truncated `user_books` on every run). Never edit an applied migration; add a new one with `supabase migration new <name>`, then `supabase db push`. Check `supabase db lint` or the dashboard advisors afterwards.

The hosted project's migration history does **not** match these filenames: migrations were applied there through the Supabase MCP/dashboard, which stamps its own timestamp (e.g. local `20260817000000_initial_schema.sql` is remote version `20260821175002`). A plain `supabase db push` will therefore refuse to run until the history is reconciled with `supabase migration repair`; compare `supabase migration list` first. Applying a new migration's SQL through the MCP `apply_migration` tool avoids that, at the cost of widening the mismatch. `20260912200000_drop_unused_profile_columns.sql` (drops `profiles.avatar_url`, the four old onboarding columns and the `avatars` bucket policies — the empty bucket itself must be deleted from the dashboard, since SQL deletes on storage tables are blocked) was written but **not yet applied** to the hosted project as of 2026-09-12 — check `list_migrations` before assuming either way. `20260914000000_book_details_tags_comments.sql` (detail/edition caches, tags, comments, owned edition, shelf order, the narrowed `touch_updated_at`) **was** applied through the MCP on 2026-09-13 as remote `book_details_tags_comments`, and `parse-command` was redeployed (v6) with the `add shelf`/`add tag`/`add comment` grammar. `20260914010000_keep_cached_page_count.sql` (remote `keep_cached_page_count`, same day) makes `cache_book_details` never replace an existing `books.page_count` — every reader's percentage hangs off it, and the volume endpoint often describes another printing.

Four migrations the client code on this branch depends on (the shelf query embeds `book_series`, and `cache_book` is called with `p_categories`) **were applied through the MCP on 2026-09-13** as remote `reading_goal_and_genres`, `book_series`, `replace_library` and `account_linking`: `20260915000000_reading_goal_and_genres` (`profiles.reading_goal`, `cache_book` stores categories and keeps an existing page count, and the **missing `reading_events` delete policy** — without it `delete <book>` never actually cleared journal lines), `20260915010000_book_series` (`book_series`, `books.series_id/series_position`, `set_book_series`), `20260915020000_replace_library` (the Goodreads import's one-transaction swap) and `20260915030000_account_linking` (`profiles.device_name/last_seen_at`, `library_summary()`, service-role-only `adopt_library`, and `touch_updated_at` ignoring owner changes). The two edge functions that go with them were deployed the same day: `parse-command` v7 (series grammar) and the new `link-account` v1, both with `verify_jwt`.

Edge functions live in [supabase/functions/](supabase/functions) and deploy with `supabase functions deploy <name>`; their secrets are set with `supabase secrets set KEY=...`.

## Architecture

### Composition root
There is a single composition root: `_BookAppState` in [lib/main.dart](lib/main.dart). It builds `GoogleBooksApiClient`, `LibraryController` (with its `BookLookupService`, `UserBookRepository`, `ReadingEventRepository`, `BookNotesRepository` and a `BookDetailsService` sharing the one Google Books client — the detail page reaches the last two through `LibraryScope` rather than a scope of its own), `MemoryController`, and `SessionService` once, then injects them downward through `LibraryScope`, `MemoryScope` and `SessionScope`. Every one has a nullable constructor-injection seam (`libraryController`, `memoryController`, `sessionService` on `BookApp`) so tests can substitute fakes without touching Supabase/Google Books/Groq. Never instantiate an HTTP client or repository inside a widget — inject it from here (or thread it down from a caller that got it from here).

`_bootstrap` opens the session *before* the first frame. There is no sign-up step: `SessionService.ensureSession()` creates an anonymous Supabase user on first launch and reuses it forever after. Everything else depends on that — every feature reads through RLS on `auth.uid()` — so a failure there is a `StartupFailureApp`, not something to carry on past. **Anonymous sign-ins must be enabled on the Supabase project** (Auth → Providers, plus `enable_anonymous_sign_ins` in `supabase/config.toml` for local runs) or a fresh install cannot start.

`_bootstrap` then reads `OnboardingStore.hasSeen()` and passes `showOnboarding` to `BookApp`, which opens on `WelcomePage` or `RootShell` accordingly. It defaults to false so a widget test gets the app itself without saying so.

### Feature-first layout
Each feature under `lib/features/<name>/` is split into `data/` (repositories/API clients), `domain/` (models, business rules), and `presentation/` (`controllers/`, `pages/`, `widgets/`). `lib/core/` holds cross-feature concerns: `env/`, `supabase/`, `ai/` (Groq client), `purchases/` (RevenueCat), `theme/`, `widgets/`.

- **library** — the reader's shelf. `LibraryController` (a `ChangeNotifier`) is the single mutation point for shelf state — status, progress, rating, owned edition and manual order — whether the change comes from a typed command, a drag on `LibraryPage`, or `BookDetailPage`; it never talks to Supabase/Google Books directly, only through `BookLookupService` (cache-first: Supabase `books` table → Google Books API → write-back), `UserBookRepository`, `BookNotesRepository` and `BookDetailsService`. Every mutation is optimistic: local state updates and notifies immediately, then persists, rolling back on failure. `ReadingStatus` has four values — `toBeRead` (`to_be_read` on the wire), `reading`, `finished`, `dnf` — rendered as four sections: "reading", "to read", "finished", "did not finish". Every successful shelf command also fires-and-forgets a `ReadingEventRepository.log` call for the streaks page — a logging failure never affects the command's own success/failure result. Tags and comments are not journaled.
  - **Shelf changes** all go through one path, `LibraryController._changeShelf` (or `moveBook`, which adds a reorder), applying `ShelfRules.enter` ([lib/features/library/domain/shelf_rules.dart](lib/features/library/domain/shelf_rules.dart)): into **to read** or **reading** → page 0 (0%); into **finished** → the last page (100%; without a page count the page stays and `completion` reads 1.0 anyway) with a finish date; into **dnf** → progress kept. Moving anywhere but finished clears `finishedAt`; the rating is kept but only *shown* while finished. `add shelf <shelf> <book>` (`addToShelf`) adds a new book at that shelf or **moves** one already on the shelf through that same path — it no longer refuses a book that's on a different shelf; only the shelf it's already on fails. `finishBook` uses the same rule. `updateProgress` changing status (a to-read book logged at page 40) does *not* reset — the typed page wins.
  - **Manual order**: `user_books.shelf_position` (null = never placed by hand). `LibraryController.section(status)` sorts via `ShelfRules.sortSection`: unplaced books first in natural (`updated_at` desc) order, then placed ones by position. `inProgress` is therefore in *shelf* order — the add tab's "currently reading" row uses `currentlyReading` (most recently updated reading book) instead, so dragging a book to the top isn't "reading it". `moveBook(id, status, index)` snapshots the whole shelf, applies the move and `ShelfRules.orderAfterDrop`, then writes `changeShelf` (if the status changed) and `saveShelfOrder` (the `set_shelf_order` RPC), rolling the entire snapshot back if either fails. Dropping a book where it started returns a failure with a null message (no pill, no haptic).
  - **Library page and drag-and-drop** (`LibraryPage`): all four sections always render once the shelf has loaded, even when empty — an empty section is its heading over a wordless outlined `_EmptyShelf` area (keyed `empty-shelf-<status>`); there is **no** instructional or "nothing here" copy anywhere, including an entirely empty library (a load *error* still replaces the shelves with the retry message). `LongPressDraggable` tiles; drop targets are signalled only by hover/active states: another tile (accent insertion bar, left half = before, right half = after), a section heading (heading turns accent; drops first in that section), or an empty shelf (outline turns accent while any book is held, thicker with a tint while hovered). Nothing appears or reflows when a drag starts. The page auto-scrolls near the top/bottom edges. While a move is saving (`_moving`), no book can be picked up (`maxSimultaneousDrags: 0`) and keyboard moves are ignored. Every move — drag, keyboard, screen reader — goes through `_move`, which catches unexpected errors, sets haptics, and shows the confirmation pill as a live region. Tiles are `FocusableActionDetector`s: Enter/Space opens the book, Alt+↑/↓ moves to the previous/next shelf, Alt+←/→ earlier/later; plus `CustomSemanticsAction`s ("Move to finished", "Move earlier"…) merged into the tile's one semantics node. Headings are semantic headers announcing their book count. A tap opens `BookDetailPage` via `openBookDetail` (route name `book_detail`).
  - **Book info page** (`BookDetailPage`, [lib/features/library/presentation/pages/book_detail_page.dart](lib/features/library/presentation/pages/book_detail_page.dart)) holds a `user_books` id, not a snapshot, and reads the row from `LibraryController.findById` every build. Layout, top to bottom: heading (cover, title as a semantic header, subtitle, author, a status line such as "reading · 78%" / "did not finish · stopped at 34%", the owned edition); a facts strip (pages, published via `formatPublishedDate`, publisher, language); a single **editions** row; "your reading" (page/percent fields kept in sync through `LibraryController.pageForPercent`, and a `StarRatingInput` that only works on finished books — keyboard arrows/Home/End, one adjustable slider node to screen readers); tags; comments (a DNF book's field asks "why didn't you finish it?"); about (blurb, genre, ISBN, Google rating). It deliberately has **no shelf picker** — moving between shelves lives on the library page and the `add shelf` command. Sections are `InfoSection` ([lib/features/library/presentation/widgets/info_section.dart](lib/features/library/presentation/widgets/info_section.dart)): `SettingsSection`'s look, with the caption announced as a heading. Everything but the shelf row is per-page state in `BookDetailController`: four independently loading `DetailSection`s (details, editions, tags, comments), so Google Books failing never blanks the reader's own notes; tag/comment edits there are optimistic with rollback, and page-level actions go through `_run`, which turns unexpected throws into a visible failure.
  - **Owned edition = the reader's copy.** `fetchLibrary` embeds the owned `book_editions` row (`owned_edition:book_editions!user_books_owned_edition_fkey(*)`) into each `LibraryBook.ownedEdition`, and `LibraryBook.displayBook` (`Book.withEdition`) is the book as *their* copy: the edition's cover, page count, publisher, published date, ISBN and language over the work's, falling back to the work only for cover and page count; title, author, blurb, genre and ratings stay the work's so commands still match. Every surface that shows a book (library tile, currently-reading card, book page) renders `displayBook`, and `LibraryBook.pageCount` — so progress, validation and "last page = finished" — follows the owned edition. `LibraryController.setOwnedEdition(id, BookEdition?)` rescales the page to keep the reader's percentage (`ShelfRules.pageForEdition`: finished stays at the new last page, an unfinished book never lands on it) and writes edition + page in one update. The shared `books` row is never changed. `_upsertLocal` keeps a row's edition when a replacement was built without one. The book page's editions row always shows the edition *count* on the right and, when one is owned, "yours: ebook · Penguin · 2010" on a second line — it must not swap one for the other.
  - **Editions page** (`EditionsPage`, opened only via `openBookEditions`, route name `book_editions`): a gallery grid of covers (`BookCover`, placeholder when Google has no image) with the publisher and format · year under each; tapping (or Enter on) a cover marks it as the owned edition through `LibraryController.setOwnedEdition`, tapping again clears it, and taps are locked while one save is in flight. It is handed the detail page's own `BookDetailController` rather than building one, so already-loaded editions show instantly and nothing is fetched twice; if editions failed or never loaded, it retries after its first frame (not in `initState` — the controller's notify would dirty the detail page mid-build). Loading, error-with-retry, empty and book-gone states are all distinct.
  - **Detail/edition caching** (`BookDetailsService`, same shape as `BookLookupService`): extended info lives in extra `books` columns, editions in the shared `book_editions` table; both are written only by security-definer RPCs (`cache_book_details`, `cache_book_editions`). A `details_fetched_at`/`editions_fetched_at` stamp on `books` — never emptiness — decides hit vs miss, so "Google has no editions for this" is cached too. The shelf's copy of a `Book` may predate a fetch, so a miss re-reads the `books` row before calling Google. Cache *reads* that fail degrade to a miss; a failed *details* write still returns what was fetched; a failed *editions* write is an error (an uncached edition has no id and can't be owned). `EditionFilter` ([lib/features/library/domain/edition_filter.dart](lib/features/library/domain/edition_filter.dart)) keeps only ebook (`saleInfo.isEbook`) and physical (a `BOOK` with an ISBN) editions whose main title matches exactly and whose author matches by name-token subset (a shared surname isn't enough — Brian Herbert's "Dune: The Heir of Caladan" is not an edition of Frank Herbert's "Dune"), dropping study guides/summaries/audio/box sets. Google's HTML blurbs go through `plainTextFromHtml` before caching.
- **logging** — the natural-language "+"/log page. `LogCommandParser` turns text into a twelve-command grammar: the original five (`start`/`update <page>`/`finish`/`rate <stars>`/`delete <title>`), the `add` family — `add shelf <tbr|reading|finished|dnf> <book>` (adds or moves a book; see **library** above — the old `add <book> tbr` form is gone), `add tag <tag> <book>` (one word, or quoted) and `add comment <comment> <book>` — plus two "cactus pro"-only commands that only ever arrive as an AI-extracted line, never typed directly — `remember <book> :: <note>` and `recommend <book> :: <reason>`. `start`/`update`/`finish` also take an optional trailing `YYYY-MM-DD` — "I started Dune yesterday" backdates the `reading_events` row it logs (and so the streaks day it lands on), never the shelf write itself, which always reflects when the command actually ran; `LibraryController` rejects a future date before it ever reaches Supabase. Resolving "yesterday" needs the reader's own local "today", which only the client can know — `EdgeFunctionCommandParser` sends it on every request as `context.today`. `AiCommandParser` ([lib/core/ai/ai_command_parser.dart](lib/core/ai/ai_command_parser.dart)) is the "cactus pro" alternative that asks an LLM to split a free-form sentence into that same grammar before handing it to the identical parser — the two entry points converge on one command surface. The real implementation calls the `parse-command` edge function; the model provider's key never reaches the device. `series <series> [#n] <book>` and `start series <series>` (see **library → series**) complete the free grammar. `delete` asks first: `HomePage._confirmDelete` shows `showConfirmDialog` ([lib/core/widgets/confirm_dialog.dart](lib/core/widgets/confirm_dialog.dart), also used by import and account linking); cancelling returns `LibraryActionResult.cancelled`, which gets no haptic and `CommandOutcome.dismissed` — the text stays in the field without a shake. `HomePage` gates `remember`/`recommend` on `PlanController.isPro` at the point they'd run, not in the parser — recognizing the syntax and being allowed to act on it are kept as two separate concerns. `recommend` never touches the shelf or the memory list: the edge function has already resolved a title and reason by the time the line reaches the client, grounded in the reader's shelf titles and `memory` notes sent as optional `context` on the same request. The `add` family puts its own argument *before* the book so the title is always the free-form tail. A quoted comment (`add comment "x" Dune`, straight or curly quotes) is split by the parser; an **unquoted** one has `title == null` and its whole argument in `note`, and `LibraryController.addComment` splits it with `splitTrailingTitle` (longest trailing run of words naming a shelf book, exact before fuzzy) — `HomePage._applyToLibrary` routes that case *before* its "no title" check, and uses the library's result message for the pill since the parser couldn't name the book. Tags/comments need the book already on the shelf. **`CommandCatalog`** ([lib/features/logging/domain/command_catalog.dart](lib/features/logging/domain/command_catalog.dart)) is the single source of command help — the parser's "did you mean" suggestions, the settings commands page and its test all read it, and `command_catalog_test.dart` parses every example; add a command there when you add one to the grammar, and to the `parse-command` prompt.
  - **Series** are shared like the catalogue: `book_series` plus `books.series_id`/`series_position`, written only by `set_book_series`, which requires the book on the caller's shelf and is **first-writer-wins** unless nobody else has that book. Every `books` read uses `Book.selectWithSeries` so the name comes along. `LibraryController.setSeries`/`startSeries` (next book in series order not finished or dropped: queued → moved to reading, absent → started, already reading one → refused) go through `BookSeriesRepository`. The library page shows a horizontally scrolling **series** row above the shelves (`SeriesGroup.fromShelf`, only when the reader has any); a group opens `SeriesPage` (route `series`), which lists every known book in the series, marking ones not on the shelf.
  - **Search**: a search icon in the library `TopBar` opens a field; `LibrarySearch.matches` requires every typed word in title/subtitle/author/series/tags (tags fetched once via `BookNotesRepository.fetchAllTags` when search opens; accents ignored). While searching, empty shelves are hidden, **nothing can be dragged**, and no match shows `no books match "…"` — the single exception to the page's no-copy rule.
- **goals** — the yearly reading goal: `profiles.reading_goal`, one number that carries across years (progress is always books finished this calendar year). `GoalController` (via `GoalScope`, built and loaded in `main.dart`, injectable as `BookApp.goalController`) is the single mutation point, optimistic with rollback. Set from onboarding's `ReadingGoalPage` or settings' **reading → yearly goal** row (`showGoalSheet`) — the stats and add pages only ever read it (`GoalProgressView(editable: false)`), so there is one place to change it. `GoalPicker` is steppers plus presets — never a `TextField` (onboarding). Tests use `test/support/fake_goals.dart`.
- **library_transfer** — CSV export and Goodreads import, both from settings' **your library** section. `LibraryExport` writes Goodreads column names plus `Current Page`, `Series`, `Series Number`, `Owned Edition` (tags as Bookshelves, comments as My Review joined by `GoodreadsImport.commentSeparator`), so an export round-trips through the import; `LibraryExporter` shares it via `share_plus`. `GoodreadsImport` parses (exclusive shelf → status, dnf-like custom shelves → DNF, `="…"` ISBNs, `(Series, #n)` in titles, other shelves → tags, review → comment). `ImportController` matches ISBN-first then title/author (4 at a time, one retry on a network error), shows a review with unmatched rows, and only after confirmation calls `replace_library` — a **full wipe** of books, tags, comments and reading events in one transaction (memories and the goal stay), then files series best-effort and calls `LibraryController.reset()`, whose `resets` stream makes the journal and the add tab's week row reload.
- **memory** — the reader's saved notes on how a book made them feel, captured by `remember` and shown on its own `MemoryPage` tab, styled as a journal the same way **streaks** below is: a book title reads in the exact face/size/color the streak journal's date labels use, and the notes under it read in the exact face/size the streak journal's command lines use — grouped by book (a note with none groups under `'general'`) rather than by day, most-recently-added-to book first, a book's own notes oldest first underneath it. That grouping happens in `MemoryPage` itself, not `MemoryController`, the same division `StreaksPage`/`StreaksController` use. `MemoryController` (a `ChangeNotifier`, injected via `MemoryScope` the same way `LibraryController` is via `LibraryScope`) is the single mutation point; `remember`/`forget` are optimistic, same convention as every `LibraryController` command. Feeds `recommend`'s grounding context — see **logging** above — but is otherwise independent of the library feature.
- **stats** (folder `streaks/`) — the "stats" tab (`StatsPage`, tab label `Stats`, same `local_fire_department_outlined` icon the streak tab always used): the goal first (`GoalProgressView`, `editable: false` — a goal is only ever changed from the **reading → yearly goal** row in settings, never from here or the add tab, so there is exactly one place to change it), then stat tiles and a monthly activity chart and genres from `ReadingStats.from(library.books)` — pure and free: books read (finished, this year by `finishedAt`, and all time), pages read (finished books in full, reading/DNF up to the page), shelf counts, average rating, a bar chart of books finished per month (`ReadingStats.booksByMonth`/`pagesByMonth`, rendered by `_ActivityChart`, current month highlighted), and top genres (`ReadingStats.genreOf` picks the first non-umbrella BISAC segment) — then the journal described next. `StreakMath` (current/best streak) is used only by the add tab's `ReadingStreak` readout now, not shown on the stats page. The journal is the old streak page, unchanged: `StreaksController` reads `reading_events` (grouped by local day, via `StreaksController.days`/`eventsFor`) and `StreaksPage` renders it as a journal, newest day first — every command reads back as a line of text in the exact face and size `CommandInput` uses on the "+" tab ("started Dune", "read up to page 240 in Dune", "finished Dune", "rated Dune 4.5 stars"), under a plain `m.d.yy` date label. `delete` events are skipped — not a moment worth journaling. `ReadingEvent.value` (a new nullable `reading_events.value` column, migration `20260911000000_reading_event_value.sql`) is what makes "up to page 240" and "4.5 stars" possible — `LibraryController` fills it in from `updateProgress`'s page and `rateBook`'s rounded rating, leaving it null for `start`/`finish`/`delete`. A day whose only command was `delete` must still count as "nothing logged" rather than rendering a blank gap — see `_Journal`'s `linesFor`-then-filter in `streaks_page.dart`, which decides that before `StreaksController.days` (day *keys*) is ever handed to a widget.
- **onboarding** — an eight-screen intro shown once per install: welcome → three tutorial pages (free-tier commands `AddBookTutorialPage` → tags & comments `TagsCommentsTutorialPage`, which also says a DNF can carry a comment with the reason → natural language) → "pick a look" → "set a goal" (`ReadingGoalPage`, skippable) → a teaser → the founder's note → finish. The progress dots have four steps: tutorial, look, goal, finish. Every tutorial page is a `TutorialStepPage` with a `CommandWall` on top (`CommandWall(rows: ...)` swaps the chips) — keep new ones built the same way, then `pushAndRemoveUntil` into `RootShell`. It is a *tour, not a gate*, and asks for nothing — no name, no email, no password — because the reader's anonymous account already exists before the first frame. `test/onboarding/intro_flow_test.dart` asserts there isn't a single `TextField` in the whole flow; keep it that way, and put anything that needs typing in settings instead. "Seen" lives on the device in `OnboardingStore`, written by `FinishPage` on the way *out* so quitting halfway doesn't burn it — it cannot live on the session, since every reader is signed in from launch one. The "pick a look" question writes to `ThemeController`, the same notifier the appearance section of settings drives, so it is a shortcut to a setting rather than separate state. The tutorial pages run an endless marquee, so tests there use fixed pumps and `ensureVisible`, never `pumpAndSettle`. "continue" on the founder's note (`FoundersNotePage`) is also where the one-time PRO paywall now shows — see **paywall** below — before handing off to `FinishPage`; `test/onboarding/founders_note_paywall_test.dart` covers that hand-off directly rather than through the full seven-screen walk, since it needs a fake `PurchasesService` the walk-through test doesn't inject.
- **paywall** — the app's one paid-upgrade surface, always a dismissible popup over whatever the reader was doing (`showPaywallPopup`, never `Navigator.push(PaywallPage(...))` directly) — it slides up from the bottom edge with a `SlideTransition`, matching the near-full-bleed card it opens, rather than fading/scaling in place. Shown once per install: `FoundersNotePage`, the last real screen of onboarding, presents it on "continue" and marks it seen first — before the popup even opens, so a reader who force-quits on it still isn't met with it again — via `IntroOfferStore` (`shared_preferences`). `RootShell`'s own copy of that same check is now a safety net rather than the primary path: for a fresh install `IntroOfferStore` is already marked seen by the time `RootShell` ever mounts, so its check is a no-op there, and only actually fires for an existing install that finished onboarding before the paywall lived there. Every one of those checks fails *closed* — an unreadable flag, an unreadable entitlement, and an existing subscriber all mean "don't show it". Outside the once-per-install show, it is only ever reached by a reader who asked: the `get cactus pro` row in settings. Its fourth chapter pitches the icon/theme customisation settings' `themes and icons` row already gates on `isPro` — see **customisation** below.
- **settings** — everything that isn't reading, behind the one gear in `TopBar`: the account, subscription state (RevenueCat Customer Center + restore), **reading** (yearly goal), **your library** (export as csv, import from goodreads), a help section whose `commands` row opens `CommandsPage` (every command from `CommandCatalog`, free and pro, route name `commands`), light/dark/system, licenses, and a `kDebugMode`-only plan override. No screen in the app uses a Material `AppBar` — settings included; it wears the same `SafeArea` + `AppSpacing.xl` gutter + lowercase `jetBrainsMono` heading as every tab. The account lives in `MembershipCard`, at the very top of the screen — a flat membership card (no photo, no name field) rather than a settings row: the "cactus" wordmark and a PRO badge on top, `profiles.created_at` underneath as "member since" (`ProfileRepository.fetchJoinedAt`) — the label renders unconditionally from the first frame, with `···` standing in for the date until the fetch resolves and `—` if it comes back empty, so the card's height never jumps once the real date lands — and the email line (a translucent pill so it stays legible over what's behind it) below that. The panel itself follows the app's own `background` token directly — paper cream in light mode, charcoal in dark — the same direction every other surface goes, rather than inverting it; what makes it read as its own object instead of blending into the page is the shadow, the border and `_WavePainter`, three low-opacity `colors.accent` sine-wave bands washing across the card's bottom third (a painted signature strip with motion to it, not a flat line — recolors instantly with the theme's own accent since it's drawn, not an asset). It is the *only* place an email is ever typed — signing up is an optional bonus offered here rather than a toll gate at the front door — and what tapping the email line does is narrow: `SessionService.linkEmail` attaches an identity to the *existing* anonymous user via `updateUser(email:)` + `verifyOTP(OtpType.emailChange)`, so the uid — and therefore the shelf, the streaks, and the RevenueCat entitlement — survives. A passwordless sign-in would provision a second account and abandon the first; don't reach for one here. There is deliberately **no sign-out** anywhere: the uid *is* the shelf, so ending an anonymous session destroys a library rather than protecting one.
  **Linking an email that already has a library** (a second device): `linkEmail` throws `EmailInUseException`; the sheet then sends a sign-in code on a *separate, in-memory* client (`sendSignInCode`/`verifySignInCode` → `PendingAccount`), so the device's own session is untouched while `LibraryConflictPage` (route `library_conflict`) shows both libraries' `library_summary()` — device name (stamped on `profiles` at startup via `DeviceName`), book count, started and last-used dates. An empty device library joins without asking. Otherwise the reader picks one and confirms deleting the other; `SessionService.keepLibrary` switches this device to the email account's session **first**, then calls the `link-account` edge function, which verifies both JWTs, runs `adopt_library` when the device's library is kept, and deletes the anonymous user. The email account's uid always survives (email, RevenueCat purchaser, other devices). `RootShell` also reloads the shelf and goal on resume after a minute away, so the other device catches up.
- **customisation** — sixteen switchable launcher icons, reached from settings' `themes and icons` row (a pro feature: free readers see it faded, and tapping it opens the paywall). `AppIcon` ([lib/core/platform/app_icon.dart](lib/core/platform/app_icon.dart)) lists them in three groups — main (`original`/`booklines`), colours (one flat colour each, no light/dark split) and themed (`clouds`/`sunset`/`triangles`) — and `CustomisationPage` shows one tile per style, applying its light or dark variant from the current theme. `AppIconController` is a global `ValueNotifier` over `AppIconChannel`, a method channel handled natively by `AppDelegate.swift` (`setAlternateIconName`, which raises iOS's own confirmation) and `MainActivity.kt` (toggling `activity-alias` entries in `AndroidManifest.xml`; Android shows a restart sheet first and closes the app after, since Recents keeps the old icon). Keep the enum, `alternateIconNames`, `componentSuffixes`, the manifest aliases and `Info.plist`'s `CFBundleAlternateIcons` in step. Previews are shaped the way the home screen shows them — the pre-cut circle (`AppIcon.roundAssetPath`) on Android (the Pixel launcher's adaptive-icon circle), the square art in a ~22% rounded square on iOS.
  The icon art lives in four places, each with a square and a circle version, all generated from the same artwork and all in the e-ink/forest-green palette below (forest-green ground and paper-cream cactus for light variants, a sage cactus for dark; the colours group keeps its own hues): `design/icons/CactusIcons/` (rounded mockups, the design source; `round/` holds the circles), `assets/app_icons/` (in-app previews; `round/` holds the circles, declared separately in pubspec.yaml since an asset directory doesn't include its subdirectories), `android/app/src/main/res/mipmap-*/ic_launcher*_base.png` (full-bleed squares used as the *background* layer of the adaptive icons in `mipmap-anydpi-v26/`, whose foreground is transparent) plus `ic_launcher*_round.png` circles and matching `*_round.xml` adaptive icons, wired up through `android:roundIcon` on the application, `MainActivity` and every alias and `ios/Runner/Assets.xcassets/` (`AppIcon.appiconset` is `originalLight`; each alternate has its own `AppIcon-*.imageset`). Changing one icon means regenerating all four copies.
- **shell** — `RootShell` hosts the four top-level pages (memory, stats, library, log) in an `IndexedStack` switched by a floating `BottomSwitcher`; log is the default tab. The **Memory tab is cactus pro**: `RootShell._selectTab` opens it when `PlanController.isPro` is set or the RevenueCat entitlement is active, and otherwise shows `showPaywallPopup` and stays on the current tab (switching to Memory if the reader buys pro in there). An entitlement check that *fails* shows the paywall (a subscriber can restore from it) rather than opening the tab for everyone. Losing pro while on Memory moves the reader to the add tab. Above the floating bar the log page shows `CurrentlyReadingCard` (the most recently active book), then a compact `GoalProgressView` (once the goal has loaded; "set a reading goal" when there is none), then `ReadingStreak` (a "N day streak" heading over the last seven days); both are read-only, hide as soon as the reader starts typing, and come back when the field empties — `ReadingStreak` is kept mounted behind `Visibility` so it doesn't re-fetch on every show/hide. All four wear the same `TopBar` — page name flush left, settings gear top right, both pixel-identical across every tab — because the gear is the app's only route to settings and a reader who can't find it on the page they're on can't find it at all; the log page's own title is `'add'` (`TopBar(title: 'add')`), with the page's own `AppSpacing.md` top inset matching the other three — a taller inset here used to sit "add" visibly lower than "library"/"stats"/"memory". `title` is required now, and `TopBar` no longer has a `center` slot — that existed only for the blue `DatePill` chip that used to sit centred on the log page reading "today"; both are gone, since the page's own `'add'` title and the tab's own `Add` semantic label already said enough. The tab bar is icon-only, so `BottomSwitcher`'s four `Semantics` labels (`Memory`/`Stats`/`Library`/`Add`) *are* the tab names, matching each page's own `TopBar` title exactly; keep them one word and title case. `SettingsHeader` (worn by `SettingsPage` and every page pushed from it, e.g. `CustomisationPage`) is not a `TopBar` — it has a back chevron instead of a gear — but follows the exact same layout, title first in an `Expanded` then the icon, so its title lands flush left at the same position rather than getting pushed right by a leading back button.

### Supabase model
`user_id` columns default to `auth.uid()` at the database level (never set by app code) and RLS is what actually enforces per-reader isolation — anonymous Supabase Auth sessions still get a real `authenticated` role. Every policy calls `(select auth.uid())`, not the bare function, so the planner evaluates it once per query rather than once per row.

- `books` — the shared Google Books cache. Readable by any signed-in reader, **writable by none**: the sole write path is the `cache_book()` security-definer function, because a table-level insert/update grant would also let any reader rewrite or delete rows out from under everyone else.
- `book_editions` — the shared edition cache, same rules as `books`: readable by any signed-in reader, written only by `cache_book_editions(book_id, jsonb)` (upserts on `(book_id, google_books_id)` so an owned edition's id survives a re-fetch; stamps `books.editions_fetched_at`). A check constraint allows only `format in ('ebook','physical')`. `books` also gained extended-info columns written only by `cache_book_details` (updates an existing row, never inserts; stamps `details_fetched_at`).
- `user_books`, `reading_events`, `profiles`, `memories`, `book_tags`, `book_comments` — private per reader. `book_tags`/`book_comments` hang off `user_books.id` (`on delete cascade`, so deleting a book takes its notes), and their insert policies also check the `user_books` row belongs to the caller; tags are unique per book on `lower(btrim(tag))`. `user_books.owned_edition_id` has a composite FK `(book_id, owned_edition_id) → book_editions(book_id, id)`, so an owned edition is always an edition of that book. `user_books.updated_at` is maintained by the `user_books_touch_updated_at` trigger, never sent from the client (the shelf is ordered by it, so a skewed device clock could otherwise pin its own rows to one end forever). That trigger (`touch_updated_at`, also used by `book_comments`) leaves `updated_at` alone for a write that changes only `shelf_position` — a drag must not change which book is "currently reading" — and clears `shelf_position` on a status change that doesn't set one. `set_shelf_order(uuid[])` is `security invoker`; RLS limits it to the caller's rows.
- `ai_requests` — the AI rate-limit ledger. RLS enabled with *no policies at all*, deliberately: it is reachable only through `claim_ai_request()`, so a reader cannot clear their own history to reset their limit.
- A trigger (`handle_new_user`) creates a blank `profiles` row on first auth, so app code only ever `UPDATE`s it. Its `EXECUTE` grant is revoked from `anon`/`authenticated` — it is a trigger function, not an API.

### Errors, logging and startup
Repositories translate driver failures into exceptions carrying a message already safe to show (`LibraryException`, `OnboardingException`, `AiCommandException`); controllers turn those into result objects. The UI never renders a raw driver error — and never silently swallows one either: a load that failed must look different from a load that came back empty (see `StreaksController.errorMessage`).

All diagnostics go through `AppLogger` ([lib/core/diagnostics/app_logger.dart](lib/core/diagnostics/app_logger.dart)) — never `print`/`debugPrint`, which are compiled out of release builds. For fire-and-forget work use `reportingFailure(...)` rather than `unawaited(x.catchError((_) {}))`, so the failure is recorded instead of dropped. `main` installs `FlutterError.onError`, `PlatformDispatcher.instance.onError` and a guarded zone, and all three feed `AppLogger`.

`CrashReporter` ([lib/core/diagnostics/crash_reporter.dart](lib/core/diagnostics/crash_reporter.dart)) attaches Firebase Crashlytics to `AppLogger.sink` — the single seam, never at individual call sites. Two rules: **never** also assign `FirebaseCrashlytics.instance.recordFlutterFatalError` to `FlutterError.onError` (Firebase's own guide says to; `main` already owns it, and doing both double-reports every framework error), and every `CrashReporter` entry point must stay inert until `attach()` succeeded — `FirebaseCrashlytics.instance` throws *synchronously* without Firebase, so an unguarded call takes out its caller rather than merely failing to report. Widget tests never run `main`, so that is the normal state in tests, not an edge case.

### Accessibility and feel
The UI is icon-heavy and text-light, which is precisely the combination that makes an app unusable with VoiceOver/TalkBack unless the labels are deliberate. The tab bar, book tiles and every day on the streak grid carry explicit `Semantics` — a book tile is *one* node reading "Dune by Frank Herbert. Page 150 of 300, 50 percent.", not six fragments ending in five unlabelled star icons. `test/accessibility/semantics_test.dart` pins these down.

Haptics go through `AppHaptics` ([lib/core/feedback/app_haptics.dart](lib/core/feedback/app_haptics.dart)) and have exactly three meanings: `selection()` (you moved), `accepted()` (it worked), `rejected()` (it didn't). Never fire one from a timer, a background event or a screen appearing — only in direct response to a touch the reader just made, and never when the outcome is a no-op (tapping the tab you are already on).

The app is portrait-only, declared in the Android manifest, the iOS plist *and* `SystemChrome` — the streaks page fits a whole year on one screen and has nowhere to put December in landscape. That page scrolls only when it must (large accessibility text sizes), never otherwise.

### Analytics
`AppAnalytics` ([lib/core/analytics/app_analytics.dart](lib/core/analytics/app_analytics.dart)) rides on the Firebase app `CrashReporter.attach()` initializes, and follows the same inert-until-attached rule for the same reason. Screen views come from `RouteSettings` names through a navigator observer on `MaterialApp` — **a new pushed route needs a `settings: const RouteSettings(name: ...)` or it disappears from the funnel silently** (the settings screen and the paywall popup both carry one). Paywall/purchase outcomes are explicit calls instead, and distinguish cancelled from store_error from entitlement_inactive, since those three call for completely different fixes.

Hard rule: **no reader-authored content is ever sent** — no titles, authors, commands, profile answers or emails. Parameters are screen names or enum-like constants only.

### Theming
`AppColors` is a `ThemeExtension` (light/dark instances in [lib/core/theme/app_colors.dart](lib/core/theme/app_colors.dart)) registered on `ThemeData.extensions` in [lib/core/theme/app_theme.dart](lib/core/theme/app_theme.dart); widgets read colors via `context.colors`, never a hardcoded hex. `ThemeController` (a `ValueListenable<ThemeMode>`) drives the `MaterialApp.themeMode` switch in `main.dart`.

## 🏗️ Production-Ready Modular Code Guidelines

### 1. Feature-First Architecture
Organize the codebase by feature domain rather than technical layers. 
*   **Good**: `features/book_tracking/`, `features/ai_summary/`, `features/library/`
*   **Avoid**: Grouping all models in one folder, all UI components in another.
This isolation ensures that changes to the AI feature don't accidentally break the core book tracking logic.

### 2. Separation of Concerns (Dumb UI)
Keep your UI components strictly focused on presentation. Extract all business logic, API calls, and data transformations into dedicated state management controllers or view-models. The UI should only listen to state changes and dispatch user actions.

### 3. Dependency Injection
Never instantiate HTTP clients or AI service classes directly inside your UI or business logic. Inject them. This makes it trivial to swap out a real AI backend for a mocked version during testing or development, avoiding unnecessary API costs.

### 4. Theme Extensions
Do not hardcode the hex values from the design system directly into UI components. Define the Light and Dark schemes centrally using theme extensions. This ensures that toggling between the Light and Dark modes updates the entire app consistently and instantly.

## 🧪 Testing Strategy

### Unit Tests
*   **Focus**: Business logic, data parsing, and AI prompt generation.
*   **Action**: Ensure that your data models accurately serialize and deserialize the AI's responses (especially if parsing JSON from an LLM). Test edge cases, such as network timeouts or malformed AI output, to ensure the app degrades gracefully rather than crashing.

### Component / UI Tests
*   **Focus**: Reusable UI elements (e.g., the accent progress ring, book cover cards, AI summary bottom sheets).
*   **Action**: Render these components in isolation. Verify that the progress bar accurately reflects 0%, 50%, and 100% states. Ensure the text contrast remains readable in both Light and Dark themes.

### Integration Tests
*   **Focus**: Core user journeys.
*   **Action**: Write end-to-end tests for the primary flows:
    1. Adding a new book to the library.
    2. Logging reading progress.
    3. Tapping the "Ask AI" button and displaying the result.
*   **Mocking**: Use mocking libraries (like `mocktail` or `mockito` in Dart/Flutter) to intercept the AI network requests during integration tests. This keeps the test suite fast, deterministic, and free from external API dependencies.
